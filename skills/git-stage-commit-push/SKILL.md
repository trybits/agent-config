# 暂存提交流程（默认不推送）

## 原则

- **只暂存本次会话的改动**：只提交本次会话中实际修改过的文件。用户明确说"提交全部"、"全都提交"时才扩大到工作区全部未提交改动。
- **独立改动分开提交**：属于不同任务，或类型明显不同（如 `feat` 与 `docs`）的改动，拆成多次提交，不复用同一条提交信息。
- **默认只提交不推送**：用户明确说"推送"、"push"、"推到远端"时才执行推送。
- **提交信息按 git 默认行为**：不额外添加任何署名、尾注。

## 步骤

1. **梳理本次改动**：汇总本次会话中编辑过的文件，逐项确认状态（`git status --porcelain -- <路径>`），把文件清单展示给用户确认。若本次会话未产生任何可提交改动，告知用户并终止。
2. **分组**：按任务/类型把确认后的文件分成一个或多个提交组，每组对应一个 `type(scope)`。判断依据：不同任务、不同类型、改动之间无逻辑关联 → 必须拆开。
3. **预检**：对每组查看真实改动内容（`git diff -- <路径>`，未跟踪文件直接读内容），检查是否混入调试代码、密钥、`.env`、大文件、临时文件；确认 `tmp/` 等临时目录已写入 `.gitignore`。发现异常先告知用户，不要擅自提交。
4. **展示提交计划**：一次性列出所有提交组——提交顺序、包含文件、完整提交文案——等用户确认后再执行，不要边提交边询问。
5. **暂存并提交**：按计划逐组执行。

   ```
   git add -- <group1 paths>
   git diff --cached --stat -- <group1 paths>   # 校验暂存范围，无改动则跳过该组
   git commit -m "..." [-m "..." ...]
   ```

   禁止使用 `git add .` / `git add -A` / `git commit -a`。
6. **收尾复核**：`git status --short` 查看剩余改动，明确告诉用户哪些改动未提交（属于用户本人或其他任务），不要顺手补交。若用户明确要求推送，再执行推送。

## 提交文案写法

   单行：`git commit -m "type(scope): 摘要"`
   多行（标题 + 正文）：标题一个 `-m`，正文每个段落独立一个 `-m`
   ```
   git commit -m "type(scope): 标题" -m "1. xxx。" -m "2. xxx。" -m "3. xxx。"
   ```

   **注意**：不要在一个 `-m` 里手动加换行符，这会导致 PowerShell 环境下正文合并为一行。每个段落用独立的 `-m` 排列即可。

   一次提交只描述本组内容，不要把其他组的事项写进同一条提交信息。

## 提交描述规范

提交描述应从**业务交付视角**出发，用业务语言说明本次完成了什么事项、产出了什么结果，而非罗列技术实现细节。

```
# 单点改动 —— subject 一行即可
type(业务/模块): 本次完成了什么事项、产出或达成什么目标

# 多项改动 —— subject 写概括性标题，body 逐条编号
type(业务/模块): 本轮工作的核心内容概括
1. 描述完成的事项、产出、调整动作，对应什么场景/诉求。
2. 同上。
...
```

- **type**：`feat` 新功能 | `fix` 修复 | `refactor` 重构 | `perf` 性能优化 | `style` 样式调整 | `docs` 文档 | `test` 测试 | `build` 构建 | `ci` CI 配置 | `chore` 杂项 | `revert` 回退 | `data` 数据更新
- **scope**：改动所属的模块 / 事项 / 任务分类名
- **subject**：用业务语言描述「本次做了什么、交付 / 产出了什么」
- **body**（多项时）：逐条列出，每条说明交付了什么内容或解决了什么问题
- **语言**：scope、subject、body 行文以中文为主。描述要清晰易懂，看的人能快速明白本次提交对应的任务、带来的变化或产出结果

## 推送（仅在用户明确要求时）

- 推送前先 `git status -sb` 确认当前分支、upstream 与领先/落后情况；落后时先告知用户，不擅自 pull/merge。
- 有 upstream：`git push`；无 upstream：`git push -u origin <当前分支>`。
- 禁止 force push，禁止跳过 hook。

## 边界处理

| 场景 | 处理 |
|------|------|
| 本次会话无可提交改动 | 告知用户，终止 |
| 用户明确要求提交全部 | 范围改为 `git status` 全量，仍先展示清单和分组计划 |
| 有改动分不清是否属于本次任务 | 列给用户判断，不擅自扩大提交范围 |
| 暂存范围与计划不符 | 停止，说明差异并重新确认 |
| hook 失败 | 修复问题后重新提交，不使用 `--no-verify` |
| 提交文案被用户拒改 | 询问修改意见，重写后再次确认 |
| 推送失败 | 报错信息，让用户决定，不自动重试 |
