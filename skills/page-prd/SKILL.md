# 「需求文档」悬浮球（page-prd）

## 背景与定位

产品原型无法直观展示业务规则与交互细节，需要配套的需求文档供开发对照，避免最终实现与原型不一致。本功能在每个页面右下角提供可拖拽的「需求文档」悬浮球，点击展开当前路由对应页面的业务规则说明（Markdown 只读展示）。

**核心约束：对既有页面代码零入侵**——只改全局布局一处挂载组件，不碰任何页面组件。

## 功能要点（已验证行为）

- 悬浮球右下角常驻，可拖到视口任意位置；**仅当前页面有规则时显示**
- 点击展开/收起面板；面板按球位置智能翻转（球在左半边 → 面板在球右侧，反之在左侧），垂直居中对齐并夹紧在视口内
- 面板支持右下角手柄拖拽调整宽高（最小 280×200）
- **左侧目录栏**：面板宽度 ≥ 680px（`TOC_BREAKPOINT`）且文档有 H2~H5 标题时显示，固定 180px、独立滚动；提取文档全部标题按层级缩进展示，点击平滑滚动定位，内容滚动时跟随高亮当前章节；面板 < 680px 时纯正文。H6 正常渲染但**不进目录**（层级过深，保持目录简洁）
- 球位置、面板尺寸、展开状态 localStorage 持久化（刷新/切页保留）
- 内容为 Markdown：每页一个 .md，Vite `?raw` 导入 + react-markdown + remark-gfm 渲染
- 移动端（<768px）不渲染

## 工作流 A：在未实现的项目中落地

适用：项目尚未实现该功能，需要按已验证模式落地。模板在 `references/implementation/`。

**第一步 前提检查**——逐项核对，任一项不满足必须说明原因并给出处理建议，不要盲目套模板：

| 检查项 | 要求 | 不满足时的处理 |
| --- | --- | --- |
| 已有类似功能 | 项目无悬浮球/侧栏式页面规则展示 | 说明已有实现可复用，重复建设没必要，终止 |
| 框架 | React 18+ / 19（react-markdown v10 要求） | 说明版本不兼容原因 |
| 样式 | Tailwind CSS（模板依赖语义色变量与 `cn()` 工具） | 说明可替换为项目色板，但模板样式类需逐一改写 |
| 路由 | react-router（`useLocation`） | 可替换为其他路由感知方式，需改造 `usePageRule` |
| 状态 | zustand + persist | 无 zustand 时改用 localStorage 直读直写（`ui-store.ts` 模板内有替换点注释） |
| 构建 | Vite（支持 `?raw` 导入 .md） | 其他打包器需换导入方案（如 esbuild text loader / 公共目录 fetch），需改造 |
| 图标 | Iconfont symbol（`cebianlanshouqi` 图标） | 无 Iconfont 时换 lucide-react 等图标，仅面板收起按钮一处使用 |

**第二步 按模板实施**：读 `references/implementation/layout-mount.md`，按其中文件清单与顺序创建/修改文件；模板组件文件可直接复制。

**第三步 验证**（项目对应启动命令，如 `pnpm dev` 浏览器实测，逐项确认）：
- 无规则页面不出现悬浮球
- 有规则页面：拖球跟手无延迟、点击展开/收起、翻转定位正确、调宽高、刷新后位置/尺寸/展开状态保留
- 目录栏：面板宽 ≥ 680px 显示目录、< 680px 隐藏且正文全宽；目录项点击平滑定位到对应章节；滚动内容时目录高亮跟随
- 悬浮球不被顶部导航遮挡（球/面板 `z-[60]`，须高于导航 z-index）
- 窗口 <768px 时悬浮球不渲染

## 工作流 B：当前页面无需求文档（询问全量/增量）

适用：目标页面**没有对应的需求文档 `.md`**（存放位置由项目结构决定，参见落地模板 `references/implementation/page-rules-readme.md`）。

1. **先询问用户**：本次写**全量需求**（覆盖页面全部行为）还是**增量需求**（只记录当前修改的部分）？这一选择决定章节骨架、版本号起点、版本说明与覆盖范围（见第 3 步）。
2. **读源码**：通读目标页面组件、对应 API 封装与 mock handler，以代码实际行为为准
3. **写内容**：按 `references/rule-writing-guide.md` 的对应规范新建 `.md`（全量 → 「二、全量需求规范」；增量 → 「三、增量需求规范」）——
   - H2 命名：`上线日期（YYYY-MM-DD）+ 需求名称`（日期与版本状态无关，修改中也带日期）
   - **全量需求**：版本号 V1.0；7 章节骨架（`1. 需求概况 / 2. 页面版本 / 3. 页面说明 / 4. 权限需求 / 5. 数据需求 / 6. 非功能性需求 / 7. 边界条件`）；**完整覆盖**页面全部行为（含本次需求与页面既有功能）；版本说明写「完整需求，覆盖页面全部行为」
   - **增量需求**：版本号从 V1.1 起（V1.0 隐含代表原页面/既有基线，不写入文档）；3 章节骨架（`1. 需求概况 / 2. 页面版本 / 3. 页面说明`），H4 章节标题以「新增：/ 变更：/ 删除：」开头标记变更类型；**只描述本次的新增/变更/删除**，不重复页面既有功能（既有行为以原页面/真实系统为准）；版本说明写「增量需求，仅记录相对已上线版本的变更，页面既有行为以已上线需求为准」
4. **注册**：在对应领域注册文件（如 `<domain>.ts`，由项目目录结构决定）追加条目：
   - 路径无动态参数 → `match`（精确）；含 `:id` → `matchPrefix`（前缀，最长者胜）
   - 无领域注册文件的页面 → 新建领域注册文件并在领域汇总入口（`index.ts` 或同等位置）合并
5. **验证**：项目启动命令（如 `pnpm dev`）进入该页面——悬浮球出现、展开内容正确渲染；相邻无规则页面确认球不显示

## 工作流 C：当前页面已有需求文档（按版本状态更新）

适用：目标页面已有 `.md`——**不再询问**，直接看最新批次的版本状态分流。**一个 H2 标题代表一个需求**；已确认/已上线的批次只增不改，新需求一律新增 H2。

1. **读现有文档**，定位最新需求批次（文档开头的第一个 H2）及其版本状态（文档结构见 `references/rule-writing-guide.md`）
2. **按版本状态分流**：
   - 最新批次为**修改中** → 直接修改该批次：更新「### 3. 页面说明」正文（增量 diff：新增/变更/删除），必要时同步版本说明；**不新增 H2、版本号不变**
   - 最新批次为**已确认 / 已上线**（或文档全部批次均已确认/上线）→ **禁止修改该批次内容**：将当前需求作为新批次，在文档开头（最顶部）**新增一个 H2**（命名 = `上线日期（YYYY-MM-DD）+ 需求名称`）+ 需求概况 + 页面版本 + 页面说明；版本号 = 最新批次 +0.1（增量批次，从 V1.1 起）；采用 3 章节骨架；状态修改中
   - **例外**：用户明确要求修改已确认/已上线批次时照做（用户手动修改例外），但动手前向用户说明该批次已被确认/已上线
3. **至多一个修改中批次**：新增批次前先检查，若文档已存在修改中批次，直接修改它而不是再新增
4. **存量旧结构文档**（带 H1 页面名 / 旧版固定维度编号 1.~9.）：不擅自改写历史内容——旧内容视为已确认历史批次保持原样，新需求按新结构插入 H2（文件顶部、无 H1 页面名）；**版本号从 V1.1 起**（旧内容视为隐含基线 V1.0，不占版本号——增量需求从 V1.1 起），并在回复中提醒用户该页文档为旧结构、可另行提出迁移
5. 确认该页面已注册（注册规则见工作流 B 第 4 步；文档存在但未注册时补注册）；完成后用项目启动命令（如 `pnpm dev`）验证渲染

## 版本状态变更

- **三档**：`修改中` / `已确认` / `已上线`
- 新建批次、新增批次状态一律为**修改中**，无需询问
- 仅当用户明确说「确认 / 定稿 / 改为已确认」时，将对应批次版本状态改为**已确认**；技能不主动建议、不自行修改状态
- 仅当用户明确说「已上线 / 上线 / 部署到生产」时，将对应批次版本状态改为**已上线**；技能不主动建议、不自行修改状态
- 「已确认」与「已上线」的差异是生命周期阶段：「已上线」= 已确认且已部署到生产

## 维护约定

- **以代码为准**：规则内容必须如实反映页面行为（含占位/未实现），页面代码改动时必须同步更新对应 `.md`；错误或过时的规则比没有规则更危险
- 模板与落地仓库的实现可能存在演进差异：落地时若目标项目中的实现组件（如 `MarkdownContent.tsx`）有更新版本，以仓库实况为准并同步模板
- 内容以纯文本 Markdown 为主，图片引用须遵守写作规范「图片引用规范」（public 绝对路径 + 渲染器 img 样式约束）；篇幅不设硬性限制——以完整覆盖规则为前提，能短则短、复杂需求可长（`?raw` 内联进 JS 产物，避免无关冗余内容）

## 写作规范

`references/rule-writing-guide.md` 是需求文档的完整写作规范，写内容前必读：

1. **文档结构（三分区）**：`rule-writing-guide.md` 分「一、通用规范」（H2 批次命名、需求概况、页面版本、版本状态三档、批次规则、多页一致性、格式约定等两章共用规则）+「二、全量需求规范」（7 章节骨架，V1.0）+「三、增量需求规范」（3 章节骨架，V1.1 起）；版本号起点与状态三档规则；同一需求多页强一致性（H2 名称 + 需求概况完全一致，**唯一差异是当前文档所属页面的那条点击路径整体加粗**（不含末尾原型路由括号），其余条目不加粗；页面版本/页面说明分撰写）
2. **「页面说明」业务模块组织**：页面说明内部按业务结构组织 H4 章节（页面布局 / 数据表格 / 弹窗 / 筛选 / 分页 / 状态清单 等），不机械套用固定维度
3. **自检清单**：写作时按九个维度（页面定位 / 加载错误空态 / 筛选 / 排序 / 分页 / 弹窗操作 / 字段枚举 / 边界条件 / 未实现）逐项核对覆盖，缺项补全——维度是检查项，不是章节标题
4. **产品原型特则**：「以代码为准」、「不写原型实现机制、只写业务规则」
