# 「需求文档」悬浮球（page-prd）

## 背景与定位

产品原型页面上的业务规则（筛选交互、分页排序、字段约束、未实现占位等）无法直观看到，真实业务开发常忽略这些规则，导致最终实现与需求不一致。本功能在每个页面右下角提供可拖拽的「需求文档」悬浮球，点击展开当前路由对应页面的业务规则说明（Markdown 只读展示），供开发对照。

**核心约束：对既有页面代码零入侵**——只改全局布局一处挂载组件，不碰任何页面组件。

## 功能要点（已验证行为）

- 悬浮球右下角常驻，可拖到视口任意位置；**仅当前页面有规则时显示**
- 点击展开/收起面板；面板按球位置智能翻转（球在左半边 → 面板在球右侧，反之在左侧），垂直居中对齐并夹紧在视口内
- 面板支持右下角手柄拖拽调整宽高（最小 280×200）
- 球位置、面板尺寸、展开状态 localStorage 持久化（刷新/切页保留）
- 内容为 Markdown：每页一个 .md，Vite `?raw` 导入 + react-markdown + remark-gfm 渲染
- 移动端（<768px）不渲染

## 工作流 A：在未实现的项目中落地

适用：项目尚未实现该功能，需要按已验证模式落地。模板在 `references/implementation/`。

**第一步 前提检查**——逐项核对，任一项不满足必须说明原因并给出处理建议，不要盲目套模板：

| 检查项 | 要求 | 不满足时的处理 |
| --- | --- | --- |
| 已有类似功能 | 项目无悬浮球/侧栏式页面规则展示 | 说明已有实现可复用，重复建设没必要，终止 |
| 框架 | React 18+ / 19（react-markdown v10 要求） | 说明版本不兼容原因 |
| 样式 | Tailwind CSS（模板依赖语义色变量与 `cn()` 工具） | 说明可替换为项目色板，但模板样式类需逐一改写 |
| 路由 | react-router（`useLocation`） | 可替换为其他路由感知方式，需改造 `usePageRule` |
| 状态 | zustand + persist | 无 zustand 时改用 localStorage 直读直写（`ui-store.ts` 模板内有替换点注释） |
| 构建 | Vite（支持 `?raw` 导入 .md） | 其他打包器需换导入方案（如 esbuild text loader / 公共目录 fetch），需改造 |
| 图标 | Iconfont symbol（`cebianlanshouqi` 图标） | 无 Iconfont 时换 lucide-react 等图标，仅面板收起按钮一处使用 |

**第二步 按模板实施**：读 `references/implementation/layout-mount.md`，按其中文件清单与顺序创建/修改文件；模板组件文件可直接复制。

**第三步 验证**（`pnpm dev` 浏览器实测，逐项确认）：
- 无规则页面（如 `/home`）不出现悬浮球
- 有规则页面：拖球跟手无延迟、点击展开/收起、翻转定位正确、调宽高、刷新后位置/尺寸/展开状态保留
- 悬浮球不被顶部导航遮挡（球/面板 `z-[60]`，须高于导航 z-index）
- 窗口 <768px 时悬浮球不渲染

## 工作流 B：既有页面无需求文档 → 完整新建

适用：目标页面在 `src/config/page-rules/content/` 下**没有 `.md`**。

1. **读源码**：通读目标页面组件、对应 API 封装与 mock handler，以代码实际行为为准
2. **写内容**：按 `references/rule-writing-guide.md` 的「文档结构（标准模板）」新建 `.md`——H1 页面名称 + 一个 H2（首个需求批次，版本号 V1.0、状态修改中）+ 需求概述 + 当前页面说明（九维度正文，**完整覆盖页面全部行为**，含本次需求与页面既有功能；需求名称/概述来自用户当前需求，名称未明确时从需求描述提炼并告知用户）
3. **注册**：在对应领域注册文件（如 `management-center.ts`）追加条目：
   - 路径无动态参数 → `match`（精确）；含 `:id` → `matchPrefix`（前缀，最长者胜）
   - 无领域注册文件的页面 → 新建领域注册文件并在 `src/config/page-rules/index.ts` 合并
4. **验证**：`pnpm dev` 进入该页面——悬浮球出现、展开内容正确渲染；相邻无规则页面确认球不显示

## 工作流 C：既有页面已有需求文档 → 按版本状态更新

适用：目标页面已有 `.md`。

1. **读现有文档**，定位最新需求批次（紧跟 H1 之后的第一个 H2）及其版本状态（文档结构见 `references/rule-writing-guide.md`）
2. **按版本状态分流**：
   - 最新批次为**修改中** → 直接修改该批次：更新「当前页面说明」正文（增量 diff：新增/变更/删除），必要时同步版本说明；**不新增 H2、版本号不变**
   - 最新批次为**已确认**（或文档全部批次均已确认）→ **禁止修改已确认批次内容**：将当前需求作为新批次，在文档开头（H1 之后）**新增一个 H2**（大概率是不同需求/不同需求批次）+ 需求概述 + 当前页面说明；版本号 = 最新批次 +0.1，状态为修改中（字段规范见写作规范）
   - **例外**：用户明确要求修改已确认批次时照做（用户手动修改例外），但动手前向用户说明该批次已被确认
3. **至多一个修改中批次**：新增批次前先检查，若文档已存在修改中批次，直接修改它而不是再新增
4. **存量旧结构文档**（无 H1 / 无需求概述字段等旧格式）：不擅自改写历史内容——旧内容视为已确认历史批次保持原样，新需求按新结构插入 H2（文档开头、H1 之后；文档无 H1 时先补上 H1 页面名称），**版本号从 V1.0 起**（旧内容无版本号，无法 +0.1），并在回复中提醒用户该页文档为旧结构、可另行提出迁移
5. 确认该页面已注册（注册规则见工作流 B 第 3 步；文档存在但未注册时补注册）；完成后 `pnpm dev` 验证渲染

## 版本状态变更

- 新建批次、新增批次状态一律为**修改中**，无需询问
- 仅当用户明确说「确认 / 定稿 / 改为已确认」时，将对应批次版本状态改为**已确认**；技能不主动建议、不自行修改状态

## 维护约定

- **以代码为准**：规则内容必须如实反映页面行为（含占位/未实现），页面代码改动时必须同步更新对应 `.md`；错误或过时的规则比没有规则更危险
- 模板与当前仓库实现可能存在演进差异：落地时若仓库 `src/components/page-rules/` 有更新版本，以仓库实况为准并同步模板
- 内容以纯文本 Markdown 为主，图片引用须遵守写作规范「图片引用规范」（public 绝对路径 + 渲染器 img 样式约束）；篇幅不设硬性限制——以完整覆盖规则为前提，能短则短、复杂需求可长（`?raw` 内联进 JS 产物，避免无关冗余内容）

## 写作规范（含文档结构）

`references/rule-writing-guide.md` 是需求文档的完整写作规范，分两大部分，写内容前必读：

1. **文档结构**：H1/H2/H3 标准模板、需求概述字段规范、需求批次与版本号规则、同一需求多页一致性
2. **「当前页面说明」正文九维度**：页面定位与数据来源、加载/错误/空态、筛选交互、排序分页、弹窗操作交互、字段与枚举、边界条件、未实现占位清单，并遵守「以代码为准」与「不写原型实现机制、只写业务规则」的产品原型特则
