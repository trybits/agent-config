# 需求文档（页面规则）内容写作规范

页面右下角「需求文档」悬浮球展示当前页面的业务规则与逻辑说明，供真实业务开发对照。本文是编写 `.md` 内容的标准规范：要求主动补全交互细节、状态清单、边界条件，并叠加产品原型特有的「以代码为准」约束。

**配套标准流程**：新增页面规则的四步流程见 `SKILL.md` 工作流 B；内容注册方式见 `implementation/page-rules-readme.md`。

## 定位与原则

- **服务对象**：后续接手真实业务开发的工程师。内容 = 页面上"看不见"的规则 + "已实现但容易误读"的行为
- **以代码为准**：如实反映页面实际行为（包括占位/未实现功能）。页面代码改动时必须同步更新；**错误或过时的规则比没有规则更危险**
- **不写纯视觉样式**（间距、颜色、字体、CSS 属性）——除非该样式承载行为含义（如操作列 sticky、容器横向滚动、truncate 截断 + Tooltip）
- **不写原型实现机制**：路由兜底分发、api 封装、接口路径与返回结构、mock 数据结构、组件/监听器实现细节等一律不写——原型如何实现开发不看，他们对照的是功能与逻辑。涉及数据来源、选项归属等业务含义时用产品语言表达，性能类提示写成非功能性需求
- 内容面向内部开发对照，勿写入机密/客户信息

## 必须覆盖的维度（逐项核对，缺项补全）

PM 和开发都容易忽略的规则往往藏在交互细节里，以下维度必须主动补全：

### 1. 页面定位与数据来源
- 入口（UI 点击路径）、访问权限（角色要求）、数据拉取时机（进入即拉 / 操作后拉）——用业务语言描述，不写路由、接口路径、返回结构等实现细节
- 数据治理规则（如选项/枚举数据是否由后台可维护配置）；数据量大时写非功能性提示（如服务端分页），不写前后端分工

### 2. 加载 / 错误 / 空态
- 加载中形态（骨架屏/转圈等 UI 形式；不写行列数等原型渲染细节）
- 失败文案与重试方式（重新加载按钮？）
- 空态文案与引导（无数据提示，有生效筛选时提供清除筛选入口）

### 3. 筛选 / 查询交互（重点，最易被忽略）
- 待应用与已生效状态是否分离？**必须点「查询」才生效？**
- 重置行为（清空哪些状态、是否回第 1 页）、隐藏的筛选行（"展开"才显示）
- 匹配规则：等值比较 / 数组 `includes` / 模糊匹配——**匹配哪些字段**（如"仅匹配名称"）
- 特殊约定值（如 `'__all__'` 表示不筛选）、Enter 等价行为
- 选项归属（筛选项等是否为后台可维护业务数据）

### 4. 排序
- 固定排序还是用户可选？字段与方向？（如"固定按 reportTime 降序"）

### 5. 分页
- 分页行为（每页条数选项、筛选/搜索变化后是否重置页码、页码越界保护）；数据量大时写非功能性提示（需支持服务端分页）

### 6. 弹窗 / 操作交互（交互细节表）
| 场景 | 必写内容 |
| --- | --- |
| 操作反馈 | 触发后立即看到什么？loading / toast / 弹窗 / 骨架屏 |
| 危险操作确认 | 删除/不可逆操作是否有二次确认弹窗？确认文案是什么？ |
| 操作失败引导 | 失败时除报错外，用户下一步怎么做（重试/修改后重试）？ |
| 占位功能 | 必须写明「占位、无提交逻辑」，如"编辑=占位弹窗（编辑功能待实现）" |
- 弹窗内**未展示的字段**也要写明（如"查看弹窗未展示 reuseType、batchLabel 等 5 个字段"）——开发会默认弹窗=全字段

### 7. 字段与枚举
- GFM 表格列全部字段：字段名 | 类型 | 说明（含格式，如 `YYYY-MM-DD`、是否为排序/匹配字段）
- 枚举值及展示映射（徽标颜色、图标含义）单独成表

## 格式约定

- 文件名：`content/<page-name>.md`，**不用 H1**（面板头部已显示标题）；单期页面正文从 H2 开始，多期页面按「版本段落」组织（见下节）
- 优先 GFM（表格、任务列表）；章节编号（`1.` `2.`）便于对照
- 不引用图片资源；篇幅不设硬性限制——以完整覆盖九个维度为前提，能短则短、复杂需求可长（`?raw` 内联进 JS 产物，避免无关冗余内容）
- 中文撰写；接口路径、字段名、枚举值用行内代码

## 多期版本结构（同一页面多期上线）

同一页面多期上线时，文档按「版本段落」组织：

- **H2 = 版本段落**：`## V1.0-20260830上线`（版本号-上线日期），正文内容从 H3 开始
- **首版 V1.0 段落 = 完整初始需求**；**后续版本段落 = 相对上一版本的增量 diff**（本期新增/变更/删除），便于开发明确每个版本要做什么
- 旧版本段落**只增不改**，保持历史原样；同一规则以**最新版本段落**为准（合并所有版本段落 = 当前完整需求）
- 原型尚未实现的内容不得写入任何版本段落（以代码为准），先在正式 PRD 中规划

## 写作流程（每页）

1. 通读页面组件源码 + 对应 API 封装 + mock handler（若有），记录实际行为
2. 对照上方 9 个维度逐项检查，缺项补全
3. 特别留意：占位功能、无点击逻辑按钮、隐藏字段、前端假分页——这些是开发最容易误读的
4. 注册并 `pnpm dev` 验证渲染（四步流程见 SKILL.md 工作流 B）
