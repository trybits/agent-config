# 需求文档（页面规则）内容写作规范

页面右下角「需求文档」悬浮球展示当前页面的业务规则与逻辑说明，供真实业务开发对照。本文定义 `.md` 的标准结构（需求批次外壳）与「页面说明」正文写作规范：要求主动补全交互细节、状态清单、边界条件，并叠加产品原型特有的「以代码为准」约束。

规范分三大区：**「一、通用规范」**为全量/增量两类需求共用；**「二、全量需求规范」**与**「三、增量需求规范」**分别定义两种骨架（7 章节 / 3 章节）。写作时按需求类型只采用其中一种，不混用。

**配套流程**：新建/更新页面规则见 `SKILL.md` 工作流 B / C；内容注册方式见 `implementation/page-rules-readme.md`。

## 一、通用规范（全量/增量需求共用）

本节规则对两种需求类型都适用。

### 文档结构概览

每个页面一个 `.md`，文件内按「需求批次」组织，每批需求一个 H2 章节。每个 H2 固定以 `1. 需求概况`、`2. 页面版本` 两个 H3 开头，第 3 章起为需求正文——骨架分两种：**全量需求 7 章节**（见「二、全量需求规范」）、**增量需求 3 章节**（见「三、增量需求规范」）。

### H2 需求批次命名

- H2 = `上线日期（YYYY-MM-DD）+ 需求名称`（如「2026-09-09 消息中心改版」，日期与名称之间一个空格）；日期与版本状态无关，**修改中批次也带日期**
- **不带 H1 页面名**——同一文件内多批次靠 H2 区分，按时间倒序排列
- **需求名称**：由用户提供，或从需求描述中提炼为一句短语；用户未明确名称时先提炼并告知用户，名称确定后保持
- 一个 H2 标题代表一个需求

### ### 1. 需求概况

- 固定字段：`需求涉及页面（按 UI 点击路径）`
- 列出**该需求涉及的全部页面**——UI 点击路径 + 原型路由（行内代码）

### ### 2. 页面版本

- 固定三个字段：**版本号** / **版本说明** / **版本状态**（三档）
- **版本号**：需求批次级，起点由需求类型决定——全量需求首个批次 → V1.0（见「二」）；增量需求首个批次 → V1.1（V1.0 隐含代表原页面/既有基线，不写入文档，见「三」）；后续新增批次 → 最新批次版本号 +0.1；同一批次内容修改**不升版本号**
- **版本说明**：全量需求写「完整需求，覆盖页面全部行为」；增量需求写「增量需求，仅记录相对已上线版本的变更，页面既有行为以已上线需求为准」（可按需补充一两句需求要点）
- **版本状态**：三档
  - **修改中**：新建/新增批次一律此状态
  - **已确认**：仅当用户明确说「确认 / 定稿 / 改为已确认」时改为该状态——技能不主动建议、不自行修改
  - **已上线**：已确认且已部署到生产，由用户标记——与「已确认」的差异是生命周期阶段

### ### 3. 页面说明

- 页面业务规则正文（必有），内部按页面业务模块自由组织 `#### N.M` 编号章节（如 `3.1`、`3.2`）——**不要用固定维度编号 1.~9.**，业务结构优先
- 组织顺序参考：页面布局概览 → 数据表格区 → 弹窗/操作 → 筛选条件区 → 分页器 → 页面状态清单

### 需求批次规则

- **排列顺序**：多个批次**按时间倒序**，最新批次紧跟文件开头，旧批次依次向下——开发打开文档第一眼即当前需求
- 同一批次处于修改中时直接改其内容，不新增批次；批次被确认后**只增不改**，新需求一律新增 H2 并插到文件开头（版本号 +0.1、状态修改中）
- 同一页面同一时刻至多一个「修改中」批次
- 从上往下读 = 最新到最旧；同一条规则以最新批次（最靠前）为准

### 同一需求多页面一致性（强约束）

一个需求涉及多个页面时，每个页面的 `.md` 强制按以下规则对齐：

- **完全一致**：`H2 需求名称` + `### 1. 需求概况`（含完整的涉及页面列表）——便于开发/测试跨页对照同一需求
- **按页面分写**：`### 2. 页面版本`（各页版本号独立递增）、`### 3. 页面说明`（按各页面分别撰写）——多页时其他页面的版本号可能不同
- 写作流程：先写主页面，再把 H2 需求名称与 `### 1. 需求概况` 原样复制到其他涉及页面

### 定位与原则

- **服务对象**：后续接手真实业务开发的工程师。内容 = 页面上"看不见"的规则 + "已实现但容易误读"的行为
- **以代码为准**：如实反映页面实际行为（包括占位/未实现功能）。页面代码改动时必须同步更新；**错误或过时的规则比没有规则更危险**
- **不写纯视觉样式**（间距、颜色、字体、CSS 属性）——除非该样式承载行为含义（如操作列 sticky、容器横向滚动、truncate 截断 + Tooltip）
- **不写原型实现机制**：路由兜底分发、api 封装、接口路径与返回结构、mock 数据结构、组件/监听器实现细节等一律不写——原型如何实现开发不看，他们对照的是功能与逻辑。涉及数据来源、选项归属等业务含义时用产品语言表达，性能类提示写成非功能性需求
- 内容面向内部开发对照，勿写入机密/客户信息

### 写作流程（每页）

1. 通读页面组件源码 + 对应 API 封装 + mock handler（若有），记录实际行为
2. 按 SKILL.md 工作流确定路径：页面无 `.md` 走工作流 B（**先询问用户全量还是增量**）；已有 `.md` 走工作流 C（按最新批次版本状态分流）
3. 按需求类型选用规范模板：全量 → 「二、全量需求规范」；增量（含已有文档新增批次） → 「三、增量需求规范」
4. 按下方「自检清单」逐项覆盖，缺项补全
5. 特别留意：占位功能、无点击逻辑按钮、隐藏字段、前端假分页——这些是开发最容易误读的
6. 「页面说明」内部按业务模块组织 H4 章节（如页面布局概览 → 数据表格 → 弹窗/操作 → 筛选 → 分页 → 状态清单）；全量需求另立第 4-7 章（权限需求 / 数据需求 / 非功能性需求 / 边界条件）；不机械套用固定维度——业务结构优先
7. 同一需求多页面时：先写主页面，再把 H2 需求名称与 `### 1. 需求概况` 原样复制到其他涉及页面
8. 注册并用项目启动命令（如 `pnpm dev`）验证渲染（流程见 SKILL.md 工作流 B）

### 自检清单（写作时逐项核对，缺项补全，不作为章节标题）

以下维度是 PM/开发都容易忽略的规则盲区，写作时**主动补全**——但按业务模块组织 H4 章节，不强制每个维度都单独成节：

#### A. 页面定位与数据来源
- 入口（UI 点击路径）、访问权限（角色要求）、数据拉取时机（进入即拉 / 操作后拉）——用业务语言描述，不写路由、接口路径、返回结构等实现细节
- 数据治理规则（如选项/枚举数据是否由后台可维护配置）；数据量大时写非功能性提示（如服务端分页），不写前后端分工

#### B. 加载 / 错误 / 空态
- 加载中形态（骨架屏/转圈等 UI 形式；不写行列数等原型渲染细节）
- 失败文案与重试方式（重新加载按钮？）
- 空态文案与引导（无数据提示，有生效筛选时提供清除筛选入口）

#### C. 筛选 / 查询交互（重点，最易被忽略）
- 待应用与已生效状态是否分离？**必须点「查询」才生效？**
- 重置行为（清空哪些状态、是否回第 1 页）、隐藏的筛选行（"展开"才显示）
- 匹配规则：等值比较 / 数组 `includes` / 模糊匹配——**匹配哪些字段**（如"仅匹配名称"）
- 特殊约定值：若实现用特定占位值表示「不筛选」之类的约定，必须写明；Enter 等价行为
- 选项归属（筛选项等是否为后台可维护业务数据）

#### D. 排序
- 固定排序还是用户可选？字段与方向？（如"固定按提交时间降序"）

#### E. 分页
- 分页行为（每页条数选项、筛选/搜索变化后是否重置页码、页码越界保护）；数据量大时写非功能性提示（需支持服务端分页）

#### F. 弹窗 / 操作交互（交互细节表）
| 场景 | 必写内容 |
| --- | --- |
| 操作反馈 | 触发后立即看到什么？loading / toast / 弹窗 / 骨架屏 |
| 危险操作确认 | 删除/不可逆操作是否有二次确认弹窗？确认文案是什么？ |
| 操作失败引导 | 失败时除报错外，用户下一步怎么做（重试/修改后重试）？ |
| 占位功能 | 必须写明「占位、无提交逻辑」，如"编辑=占位弹窗（编辑功能待实现）" |
- 弹窗内**未展示的字段**也要写明（如「查看弹窗未展示 XX、YY 等 N 个字段」）——开发会默认弹窗=全字段

#### G. 字段与枚举
- GFM 表格列全部字段：字段名 | 类型 | 说明（含格式，如 `YYYY-MM-DD`、是否为排序/匹配字段）
- 枚举值及展示映射（徽标颜色、图标含义）单独成表

#### H. 边界条件（逐一列出，不能省略）
- 内容为空时：
- 内容超长时（截断 + Tooltip？）：如长文本列 truncate + hover Tooltip
- 网络异常或请求超时时：
- 无权限时：
- 并发操作时（多人同时操作同一条数据）：
- 数据格式不符时：

#### I. 未实现 / 占位清单
- 集中表格列出当前页面所有占位功能：功能 | 当前状态（占位弹窗 / 无点击逻辑 / 字段未展示），避免开发误以为已实现

### 格式约定

- 文件名：`<content-dir>/<page-name>.md`（`<content-dir>` 是项目里存放需求文档的目录，由落地模板 `references/implementation/page-rules-readme.md` 决定）；面板头部另有注册 title 入口标题（如「<页面名> · 需求文档」），与文档内 H2 需求名称区分
- 结构层级：`## YYYY-MM-DD 需求名称` → `### N. 需求概况 / 页面版本 / 页面说明`（全量需求另加第 4-7 章，见「二」） → `#### N.M 业务模块` → `##### N.M.K 子项` → `###### N.M.K.L 操作项`；业务模块自由组织
- H5 正常渲染、进目录；H6 正常渲染但**不进目录**（层级过深，保持目录简洁）
- **章节层级硬上限 H6**——超过 H6 的内容用**列表项**或**加粗段落**表达，不要再加标题层级。H7+ 在渲染器（react-markdown v10）中被降级为普通文本/段落（不是合法 heading），无锚点、不进目录、不被高亮跟随。这是有意为之的"写错信号"：业务文档的合理深度是「模块 → 弹窗 → 操作项」三层（H4-H6），再往下应该用列表/加粗而非再加标题。如果发现 H7+ 普遍出现，说明结构需要重构
- 优先 GFM（表格、任务列表）；章节编号（`3.1` `3.2`）便于对照
- 图片引用见「图片引用规范」一节；篇幅不设硬性限制——以完整覆盖规则为前提，能短则短、复杂需求可长（`?raw` 内联进 JS 产物，避免无关冗余内容）
- 中文撰写；接口路径、字段名、枚举值用行内代码
- 渲染注意：`h4`/`h5`/`h6`（章节与子项标题）及 `img` 样式已内置落地模板 `MarkdownContent.tsx`（H6 渲染但不进目录）；目标项目若用旧版渲染器（未含以上样式），先同步模板版本再使用

### 图片引用规范

`?raw` 内联的 Markdown 字符串不经过构建工具资源打包、渲染时相对路径随路由漂移，因此图片引用必须遵守以下约定，否则构建后 404：

**使用原则**
- 图片只承载「文字难以表达」的信息（复杂布局/交互流程示意、字段对照截图）；能用文字说清的规则一律不用图
- 图片必须是业务规则的一部分，不用于视觉装饰（呼应「不写纯视觉样式」）
- 截图内容同样纳入「以代码为准」的同步范围：页面行为变更涉及图中内容时**必须同步更新图片**——图片过期比文字过期更危险（文字矛盾一眼可见，截图过期看起来像"本来就这样"）

**引用方式**
- 图片文件放 `public/page-rules/<page-name>/`（public 下独立子目录：避免与业务资源重名、迁移时整体拷贝）
- 文档中用**绝对路径**引用（构建后稳定、不随路由变化）：
  `![说明文字](/page-rules/<page-name>/xxx.png)`
- **alt 说明文字必写**——开发对照用，图片加载失败时仍可读
- 文件名用语义化英文（如 `detail-dialog-layout.png`），不用中文与空格

**渲染要求**
- 渲染器需为 `img` 提供样式约束（`max-width: 100%` + 圆角描边，落地模板 `MarkdownContent.tsx` 已内置），否则图片可能撑破面板
- 目标项目的 `MarkdownContent.tsx` 若未内置 img 样式，引用图片前先同步模板版本

## 二、全量需求规范（7 章节骨架）

**适用**：页面无 `.md` 且用户选择**全量需求**（工作流 B 的询问结果）。

- **版本号**：V1.0——文档即页面完整记录
- **版本说明**：「完整需求，覆盖页面全部行为」
- **覆盖范围**：**完整覆盖**页面全部行为（含本次需求与页面既有功能）
- **骨架** = 7 章节：`1. 需求概况 / 2. 页面版本 / 3. 页面说明 / 4. 权限需求 / 5. 数据需求 / 6. 非功能性需求 / 7. 边界条件`

```markdown
## YYYY-MM-DD 需求名称

### 1. 需求概况

- 需求涉及页面（按 UI 点击路径）：
  1. 父菜单 → 子菜单 → 页面名（原型路由 `/<page-path>`）
  2. 父菜单 → 页面名（原型路由 `/<page-path>`）

### 2. 页面版本

- 版本号：V1.0
- 版本说明：完整需求，覆盖页面全部行为
- 版本状态：修改中

### 3. 页面说明

#### 3.1. 页面布局概览

| 区域 | 说明 |
| --- | --- |
| …… | …… |

#### 3.2. 数据表格区

##### 3.2.1. 字段说明

……

### 4. 权限需求

……

### 5. 数据需求

……

### 6. 非功能性需求

……

### 7. 边界条件

……
```

第 4-7 章与「自检清单」对应：权限需求 ↔ A（访问权限）、数据需求 ↔ A（数据治理）与 G（字段枚举）、非功能性需求 ↔ A/E（服务端分页等性能提示）、边界条件 ↔ H（边界条件）。

## 三、增量需求规范（3 章节骨架）

**适用**：页面无 `.md` 且用户选择**增量需求**（工作流 B 的询问结果）；或页面已有文档需**新增批次**（工作流 C，已确认/已上线批次禁止修改时）。

- **版本号**：首个批次 V1.1（**无论页面有无 `.md`**，V1.0 隐含代表原页面/既有基线，不写入文档）；后续新增批次 → 最新批次 +0.1
- **版本说明**：「增量需求，仅记录相对已上线版本的变更，页面既有行为以已上线需求为准」
- **覆盖范围**：只描述本次的**新增/变更/删除**，不重复页面既有功能（既有行为以原页面/已上线需求为准）
- **相对基准**：页面无既有文档 → 相对**原页面**（真实系统现状）；已有文档新增批次 → 相对**已上线/上一批次**
- **H4 章节标题**以「新增：/ 变更：/ 删除：」开头标记变更类型
- **骨架到第 3 章为止**，无第 4-7 章

```markdown
## YYYY-MM-DD 需求名称

### 1. 需求概况

- 需求涉及页面（按 UI 点击路径）：
  1. 父菜单 → 页面名（原型路由 `/<page-path>`）

### 2. 页面版本

- 版本号：V1.1
- 版本说明：增量需求，仅记录相对已上线版本的变更，页面既有行为以已上线需求为准
- 版本状态：修改中

### 3. 页面说明

#### 3.1. 新增：……

#### 3.2. 变更：……
```
