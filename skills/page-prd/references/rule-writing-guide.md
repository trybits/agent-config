# 需求文档（页面规则）内容写作规范

页面右下角「需求文档」悬浮球展示当前页面的业务规则与逻辑说明，供真实业务开发对照。本文定义 `.md` 的标准结构（需求批次外壳）与「当前页面说明」正文写作规范（九维度）：要求主动补全交互细节、状态清单、边界条件，并叠加产品原型特有的「以代码为准」约束。

**配套流程**：新建/更新页面规则见 `SKILL.md` 工作流 B / C；内容注册方式见 `implementation/page-rules-readme.md`。

## 文档结构（标准模板）

每个页面一个 `.md`，文件内按「需求批次」组织，每批需求一个二级标题：

```markdown
# 智能体监控

## 2026-08-30 智能体监控新增评级筛选

### 需求概述

- 版本号：V1.1
- 版本说明：增量需求，仅记录相对已上线版本的变更
- 版本状态：修改中
- 需求涉及页面（按 UI 点击路径）：
  1. 管理中心 → 智能体监控 → 全部智能体（原型路由 `/management-center/agent-monitor/summary`）
  2. 管理中心 → 应用评测分级（原型路由 `/management-center/agent-eval/list`）

### 当前页面说明

#### 1. 页面定位与数据来源

……

#### 2. 页面状态清单

……
```

### 层级与字段规则

| 层级 | 内容 | 规则 |
| --- | --- | --- |
| `# 页面名称` | 页面名 | H1 = 页面名称（如「智能体监控」），与注册文件 title 的**页面名部分**一致（title 形如「智能体监控 · 需求文档」时，H1 只写页面名）；一个文件一个 H1 |
| `## 上线时间 需求名称` | 一个需求批次 | 上线时间确认时写 `2026-08-30 需求名称`（`YYYY-MM-DD` + 空格）；**未确认时省略日期只写需求名称**；时间确认后补到标题前；**多个批次按时间倒序排列，最新批次紧跟 H1 之后** |
| `### 需求概述` | 批次元信息 | 固定四个字段（见下），字段项不可增删改名；**不设上线时间字段** |
| `### 当前页面说明` | 页面业务规则正文 | 按下方九维度撰写，维度章节用 `####`（H4） |

### 需求概述字段

- **版本号**：需求批次级。页面首个批次 V1.0，后续每新增一个批次 +0.1（V1.0 → V1.1 → V1.2）；同一批次内容修改**不升版本号**
- **版本说明**：首版写「完整需求，覆盖页面全部行为」；后续批次写「增量需求，仅记录相对已上线版本的变更」（可按需补充一两句需求要点）
- **版本状态**：修改中 / 已确认。新建批次一律**修改中**；仅用户明确要求时才改为已确认；状态只标记在概述字段中，**不体现在 H2 标题里**
- **需求涉及页面（按 UI 点击路径）**：列出**该需求涉及的全部页面**——UI 界面点击路径 + 原型路由（行内代码）；同一需求多页面时每个页面的此字段内容一致

### 需求批次规则

- **排列顺序**：多个批次**按时间倒序**，最新批次紧跟 H1 之后，旧批次依次向下——开发打开文档第一眼即当前需求
- **首版批次 = 页面全量需求**：该页所有行为（含本次需求与页面既有功能）完整写入「当前页面说明」
- **后续批次 = 相对上一批次的增量 diff**（新增/变更/删除），便于开发明确每个批次要做什么；未在本批次变更的行为见更早批次，不重复书写
- 同一批次处于修改中时直接改其内容，不新增批次；批次被确认后**只增不改**，新需求一律新增 H2 并插到文档开头（H1 之后）（版本号 +0.1、状态修改中）
- **存量旧结构文档**（无 H1/无需求概述字段）的旧内容无版本号：首个按新结构插入的批次**版本号从 V1.0 起**，后续批次照常 +0.1
- 同一页面同一时刻至多一个「修改中」批次
- 从上往下读 = 最新到最旧；同一条规则以最新批次（最靠前）为准
- **需求名称**：由用户提供，或从需求描述中提炼为一句短语（如「智能体监控新增评级筛选」）；用户未明确名称时先提炼并告知用户，名称确定后保持（多页面一致性依赖名称一致）

### 同一需求多页面一致性

一个需求涉及多个页面时，**每个页面的 H2 需求名称与 H3 需求概述必须完全一致**（含涉及页面字段列出的完整页面列表），便于开发/测试跨页对照同一需求；仅「当前页面说明」按各页面分别撰写。

## 定位与原则

- **服务对象**：后续接手真实业务开发的工程师。内容 = 页面上"看不见"的规则 + "已实现但容易误读"的行为
- **以代码为准**：如实反映页面实际行为（包括占位/未实现功能）。页面代码改动时必须同步更新；**错误或过时的规则比没有规则更危险**
- **不写纯视觉样式**（间距、颜色、字体、CSS 属性）——除非该样式承载行为含义（如操作列 sticky、容器横向滚动、truncate 截断 + Tooltip）
- **不写原型实现机制**：路由兜底分发、api 封装、接口路径与返回结构、mock 数据结构、组件/监听器实现细节等一律不写——原型如何实现开发不看，他们对照的是功能与逻辑。涉及数据来源、选项归属等业务含义时用产品语言表达，性能类提示写成非功能性需求
- 内容面向内部开发对照，勿写入机密/客户信息

## 「当前页面说明」必须覆盖的维度（逐项核对，缺项补全）

PM 和开发都容易忽略的规则往往藏在交互细节里，以下维度必须主动补全（文档中作为「当前页面说明」下的 `#### N.` 章节）：

#### 1. 页面定位与数据来源
- 入口（UI 点击路径）、访问权限（角色要求）、数据拉取时机（进入即拉 / 操作后拉）——用业务语言描述，不写路由、接口路径、返回结构等实现细节
- 数据治理规则（如选项/枚举数据是否由后台可维护配置）；数据量大时写非功能性提示（如服务端分页），不写前后端分工

#### 2. 加载 / 错误 / 空态
- 加载中形态（骨架屏/转圈等 UI 形式；不写行列数等原型渲染细节）
- 失败文案与重试方式（重新加载按钮？）
- 空态文案与引导（无数据提示，有生效筛选时提供清除筛选入口）

#### 3. 筛选 / 查询交互（重点，最易被忽略）
- 待应用与已生效状态是否分离？**必须点「查询」才生效？**
- 重置行为（清空哪些状态、是否回第 1 页）、隐藏的筛选行（"展开"才显示）
- 匹配规则：等值比较 / 数组 `includes` / 模糊匹配——**匹配哪些字段**（如"仅匹配名称"）
- 特殊约定值（如 `'__all__'` 表示不筛选）、Enter 等价行为
- 选项归属（筛选项等是否为后台可维护业务数据）

#### 4. 排序
- 固定排序还是用户可选？字段与方向？（如"固定按 reportTime 降序"）

#### 5. 分页
- 分页行为（每页条数选项、筛选/搜索变化后是否重置页码、页码越界保护）；数据量大时写非功能性提示（需支持服务端分页）

#### 6. 弹窗 / 操作交互（交互细节表）
| 场景 | 必写内容 |
| --- | --- |
| 操作反馈 | 触发后立即看到什么？loading / toast / 弹窗 / 骨架屏 |
| 危险操作确认 | 删除/不可逆操作是否有二次确认弹窗？确认文案是什么？ |
| 操作失败引导 | 失败时除报错外，用户下一步怎么做（重试/修改后重试）？ |
| 占位功能 | 必须写明「占位、无提交逻辑」，如"编辑=占位弹窗（编辑功能待实现）" |
- 弹窗内**未展示的字段**也要写明（如"查看弹窗未展示 reuseType、batchLabel 等 5 个字段"）——开发会默认弹窗=全字段

#### 7. 字段与枚举
- GFM 表格列全部字段：字段名 | 类型 | 说明（含格式，如 `YYYY-MM-DD`、是否为排序/匹配字段）
- 枚举值及展示映射（徽标颜色、图标含义）单独成表

#### 8. 边界条件（逐一列出，不能省略）
- 内容为空时：
- 内容超长时（截断 + Tooltip？）：如长文本列 truncate + hover Tooltip
- 网络异常或请求超时时：
- 无权限时：
- 并发操作时（多人同时操作同一条数据）：
- 数据格式不符时：

#### 9. 未实现 / 占位清单
- 集中表格列出当前页面所有占位功能：功能 | 当前状态（占位弹窗 / 无点击逻辑 / 字段未展示），避免开发误以为已实现

## 格式约定

- 文件名：`content/<page-name>.md`；H1 = 页面名称（面板头部另有注册 title 入口标题，两者并存：title 形如「页面名 · 需求文档」，H1 只写页面名）
- 结构层级固定：H1 页面名 → H2 需求批次 → H3 需求概述 / 当前页面说明 → `#### N.` 九维度章节；**不要把维度章节写成 H3**，避免与「需求概述/当前页面说明」平级混淆
- 优先 GFM（表格、任务列表）；章节编号（`1.` `2.`）便于对照
- 图片引用见「图片引用规范」一节；篇幅不设硬性限制——以完整覆盖九维度为前提，能短则短、复杂需求可长（`?raw` 内联进 JS 产物，避免无关冗余内容）
- 中文撰写；接口路径、字段名、枚举值用行内代码
- 渲染注意：`h4`（九维度章节）与 `img` 样式已内置落地模板 `MarkdownContent.tsx`；目标项目若用旧版渲染器（未含二者），先同步模板版本再引用图片/写 `####` 章节

## 图片引用规范

`?raw` 内联的 Markdown 字符串不经过 Vite 资源打包、渲染时相对路径随路由漂移，因此图片引用必须遵守以下约定，否则构建后 404：

**使用原则**
- 图片只承载「文字难以表达」的信息（复杂布局/交互流程示意、字段对照截图）；能用文字说清的规则一律不用图
- 图片必须是业务规则的一部分，不用于视觉装饰（呼应「不写纯视觉样式」）
- 截图内容同样纳入「以代码为准」的同步范围：页面行为变更涉及图中内容时**必须同步更新图片**——图片过期比文字过期更危险（文字矛盾一眼可见，截图过期看起来像"本来就这样"）

**引用方式**
- 图片文件放 `public/page-rules/<page-name>/`（public 下独立子目录：避免与业务资源重名、迁移时整体拷贝）
- 文档中用**绝对路径**引用（构建后稳定、不随路由变化）：
  `![说明文字](/page-rules/<page-name>/xxx.png)`
- **alt 说明文字必写**——开发对照用，图片加载失败时仍可读
- 文件名用语义化英文（如 `eval-dialog-layout.png`），不用中文与空格

**渲染要求**
- 渲染器需为 `img` 提供样式约束（`max-width: 100%` + 圆角描边，落地模板 `MarkdownContent.tsx` 已内置），否则图片可能撑破面板
- 本仓库 `src/components/page-rules/MarkdownContent.tsx` 若未内置 img 样式，引用图片前先同步模板版本

## 写作流程（每页）

1. 通读页面组件源码 + 对应 API 封装 + mock handler（若有），记录实际行为
2. 按 SKILL.md 工作流 B / C 确定新建还是更新、更新哪个批次（修改中批次 vs 新增 H2）
3. 对照上方 9 个维度逐项检查，缺项补全
4. 特别留意：占位功能、无点击逻辑按钮、隐藏字段、前端假分页——这些是开发最容易误读的
5. 同一需求多页面时：先写主页面，再把 H2 需求名称与 H3 需求概述原样复制到其他涉及页面
6. 注册并 `pnpm dev` 验证渲染（流程见 SKILL.md 工作流 B）
